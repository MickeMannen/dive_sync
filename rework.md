# Dive Sync Redesign Plan

## Two-track split

**Track A — Docker: scheduled-sync-only engine.** Drops the interactive dashboard down to a read-only status page + a small schedule-config form. No dive editing there anymore.

**Track B — Desktop app: native Toga GUI (macOS → Windows/Linux), Briefcase-packaged.** No terminal component (unlike UWMedia's dual GUI/CLI build — this is GUI-only, single Briefcase app target). Owns manual sync + all dive editing.

Both tracks import `src/core` (`adapter.py`, `sync_engine.py`, `models.py`, `mapping/`, `services/`) unchanged — that layer is already adapter-abstracted and doesn't know about FastAPI or Toga, so it's the shared library UWMedia's `sources = [...]` pattern in `pyproject.toml` mirrors.

---

## Track A: Docker changes

1. **Extract `scheduler_loop()`** out of `src/web/app.py` into `src/core/scheduler.py` — it currently only reads `SettingsModel.cron_jobs`/`schedule` and calls into the sync engine, nothing FastAPI-specific about it. This makes it callable from a slim entrypoint without dragging in the full web app.
2. **Trim `src/web/app.py`** (or add a new `src/web/status_app.py`) to expose:
   - Read-only: last sync timestamp/result per account, recent log tail (reuse the existing SSE logging plumbing), next scheduled run.
   - Write: only the schedule/`cron_jobs` config endpoints (already modeled by `CronJobModel`/`SyncScheduleSlot` in `config.py`) — no dive/cache endpoints, no delete flow.
3. Remove dive-editing routes and the local cache explorer from the Docker-facing app; that code either deletes or gets ported into the desktop app (see Track B).
4. `docker_run.py`/`Dockerfile` otherwise unchanged — still boots one process that runs the scheduler loop + the trimmed status server.
5. Update `DOCKERHUB.md`/`README.md` deployment docs to describe the new scope (scheduled sync + status, not a dashboard).

## Track B: Desktop app (Briefcase + Toga)

**Structure**, following UWMedia's `pyproject.toml` layout:
```
dive_sync/
├── src/core/            # shared, untouched
├── desktop/             # new — Toga app package
│   ├── app.py           # DiveSyncApp(toga.App), sidebar + section-swap like UWMedia
│   ├── sections/        # sync_section.py, garmin_editor.py, divelogs_editor.py, settings.py
│   └── credentials.py   # keyring-backed credential store
├── pyproject.toml       # [tool.briefcase] — mac first, win/linux sections added later
```

**UX, carried over from UWMedia:**
- Sidebar nav + swapped content sections (Sync, Garmin Dives, Divelogs Dives, Settings) instead of tabs.
- `toga.Table` grids for the dive list/editor (mirrors the tag-editor and HUD-designer tables), inline field editing for buddy/weights/visibility/location/notes/dive-number — same fields the current web spreadsheet editor exposes.
- Long-running sync runs as a background task with streamed progress lines into a log panel + progress bar, same pattern as UWMedia's Convert/Process "Run" flow — except here it can stay in-process (async call into `sync_engine`) rather than relaunching a subprocess, since there's no bundled ffmpeg-style external binary involved.
- "Sync now" is manual only — no built-in scheduler in the app itself, per your call; scheduled/unattended sync stays Docker's job.

**Credentials:** stored via `keyring` (OS keychain — Keychain/Credential Manager/Secret Service), a new `desktop/credentials.py` wrapper around the existing `GarminCredentials`/`DivelogsCredentials` Pydantic models — the desktop app populates those models from keychain instead of `credentials.json`. Docker keeps the current file-based `credentials.json`/env-var approach unchanged (it's headless).

**Deferred to phase 2:** depth/temperature/gas telemetry graphs (v1 ships metadata editing only), Windows/Linux Briefcase targets and any code-signing/notarization setup (macOS first, matching UWMedia's primary target).

## Cross-cutting: concurrent runners on different machines

Docker (server/NAS) and desktop app (laptop) may sync the same account independently with no shared filesystem, so:
- No cross-process lock is possible or attempted — each keeps its own local cache/`sync_state.json`, scoped to its own machine.
- Both already need to honor `api_cooldown_seconds`/backoff on Garmin's 429s (existing constraint in `AGENTS.md`); no new coordination mechanism, just make sure both entry points still route through the same rate-limit-aware adapter code path.
- Document this in README as a known limitation: back-to-back manual desktop syncs shortly before/after a scheduled Docker run on the same account can still hit rate limits — user manages timing, the system doesn't arbitrate it.

2. ✅ Stand up the Briefcase/Toga skeleton (`desktop/app.py`, sidebar shell, empty sections) — validate packaging on macOS early, same way UWMedia did.
   - `pyproject.toml` (`[tool.briefcase.app.desktop]`) + `desktop/` package: `app.py` (sidebar/section-swap, copied from UWMedia's proven pattern), `theme.py`, `widgets.py`, `sections/{sync,garmin,divelogs,settings}.py` (placeholders).
   - Validated both `briefcase dev` and a real `briefcase create/build macOS` → launched the packaged `DiveSync.app` standalone (own process, own menu bar) and confirmed it renders correctly.
   - Desktop app depends only on `src/core` (not `src/web`, which needs fastapi/uvicorn); `sources = ["src"]` in `pyproject.toml` because Briefcase copies each source by its *basename* — a nested `"src/core"` entry would flatten to a bare `core/` folder and break `from src.core.X import ...`.
3. ✅ Build the Sync section (manual sync, log streaming, progress).
   - `desktop/sections/sync.py` (`SyncSection`): direction selector + dry-run/only-new/sync-gases/sync-fit switches, a "Sync now" button, an indeterminate `toga.ProgressBar`, and a read-only `toga.MultilineTextInput` log panel.
   - Reuses `src/core/scheduler.run_sync_thread()` directly (same function the Docker scheduler uses) via a background `threading.Thread`, so there's exactly one place that knows how to apply directionality/filter overrides and call `SyncEngine`.
   - `desktop/logging_bridge.py` attaches a queue-backed `logging.Handler` to the shared `"dive_sync"` logger at app startup (`DiveSyncApp.startup()` → `app.log_queue`) — the same technique as `src/web/app.py`'s SSE handler, just polled by an `async def on_run` loop instead of streamed over HTTP.
   - Verified live in a running window (button disables → progress bar starts → log lines stream in in real time → button re-enables with a final "Sync complete."/"Failed: …" status) using a throwaway smoke-test script that monkeypatches `SyncEngine.run_sync` — deliberately never touched the real `credentials.json` (which holds live Garmin/Divelogs accounts) or made any network call.
4. ✅ Build Garmin/Divelogs editor sections (table + field editing, reusing `update_dive`/`delete_dive` from adapters).
   - `src/core/dive_cache.py` (new, 10 unit tests in `tests/test_dive_cache.py`): ports the local-cache read/list/update/delete + remote-push logic that used to live directly in `src/web/app.py` before milestone 1 trimmed it out — `list_garmin_dives`/`list_divelogs_dives`, `read_raw_dive`, `update_dive_fields`, `delete_dive_local`, `push_remote_update`, `push_remote_delete`. This is now the one place that understands the raw Garmin/Divelogs JSON shapes; both a future web view and the desktop app can reuse it instead of duplicating field-mapping logic.
   - `desktop/sections/dive_editor.py` (`DiveEditorSection`, shared by both services since they're identical apart from which adapter/cache functions they call): a `toga.Table` dive list (Date/Time, Dive #, Location, Max Depth, Duration, Buddy, Weight, Visibility) + a detail form (adds Notes) that populates on row selection; Save and Delete each run in a background thread with the same `threading.Thread` + `asyncio.sleep(0.1)`-poll pattern as the Sync section, and both bail out with a status message if `scheduler.is_sync_running` (avoids racing a full sync's cache writes). Delete confirms via `toga.ConfirmDialog` first.
   - `desktop/sections/garmin.py`/`divelogs.py` are now thin wrappers instantiating `DiveEditorSection` with `service="garmin"`/`"divelogs"`.
   - Verified live end-to-end against fake dive files + fake credentials (`DATA_DIR` pointed at a scratch dir, both adapters monkeypatched so no real network call was possible): selected the row (form populated correctly with every field), edited Location, clicked Save (file rewritten on disk with correct nested `summary`/`details` updates, table refreshed to show the new value), reselected the row, clicked Delete, confirmed the `ConfirmDialog` text was correct, clicked OK, and confirmed the file was removed from disk and the table went empty. Row-selection had to be driven via the accessibility `select` action rather than `click` (Toga's `Table` rows don't expose an `AXPress` action on this backend, so a plain click silently no-ops); the `ConfirmDialog`'s buttons live under `sheet 1 of window 1`, not the window's top-level buttons.
5. ✅ Wire up keychain credential storage + first-run setup flow.
   - `desktop/paths.py`: `configure_environment()` points `src.core.config`'s file-based `SETTINGS_FILE`/`CREDENTIALS_FILE` at this app's private per-user data directory (via `platformdirs`, e.g. `~/Library/Application Support/DiveSync` on macOS) instead of the cwd. Called from `desktop/__main__.py` *before* `desktop.app` (and anything under `src.core`) is imported, since those paths are computed once at import time.
   - `desktop/credentials.py`: wraps `keyring` (OS keychain) as the desktop app's only durable credential store — `load_credentials_model()`/`save_credentials_model()`/`has_any_credentials()`. 8 unit tests in `tests/test_desktop_credentials.py` against a fake in-memory keyring backend.
   - `desktop/sections/settings.py` is now a real Settings section: Garmin + Divelogs credential forms (username/password/token dir), a "Test" button per service (reuses `GarminAdapter`/`DivelogsAdapter.login()` via the new `desktop/async_utils.run_in_thread` helper — extracted from `DiveEditorSection`'s identical polling snippet), and a "Save credentials" button. Password fields never get prefilled with the real secret (blank = "keep what's already saved"); the banner text changes to a first-run welcome message when no credentials exist yet, and `DiveSyncApp.startup()` lands on Settings instead of Sync on first run.
   - **Real finding, not cosmetic**: `SyncEngine`/`dive_cache` only know how to authenticate by reading a JSON file (`ConfigManager.load_credentials()`), so keychain-sourced credentials still have to be materialized to disk for `SyncEngine`/adapter calls to work. The original plan was "materialize once at startup, delete on exit" — that turned out to be unreliable: **toga-cocoa 0.5.6 does not wire the native Quit menu item or Cmd+Q to `App.on_exit`/`request_exit` at all** (`NSApplication`'s default `terminate:` handles those directly, ending the process before any Python shutdown code — including `atexit` callbacks — gets a chance to run; verified empirically both ways, `on_exit` and `atexit` both silently never fired on a real quit). Redesigned around a reference-counted `begin_operation()`/`end_operation()` pair in `desktop/credentials.py` instead: the credentials file now only exists on disk for the actual duration of a sync or a dive save/delete (wrapped in `try`/`finally` in `sync.py`'s `on_run` and `dive_editor.py`'s `on_save`/`on_delete`), not for the app's whole lifetime. `atexit` is still registered as a last-resort safety net for an unbalanced counter (e.g. a crash mid-operation), on the (unproven) chance it fires on some exit paths even though it didn't on a plain Cmd+Q.
   - Verified live end-to-end with real keychain writes (under a distinct "DiveSync" service name — never touched the project's real `credentials.json`/its real accounts) and a mocked `SyncEngine.run_sync` for the sync-triggered materialization check: first run correctly lands on Settings with the welcome banner; typed fake credentials actually landed in the real macOS Keychain (verified via `keyring.get_password` directly, including the password — the accessibility layer's blanked-out readback of secure text fields is cosmetic only); Save materializes+writes `credentials.json` into the private data dir with correct structure; "Test" correctly ran a real (backgrounded, non-blocking) Garmin login attempt against the typed fake credentials and reported "Login failed."; opening the app and browsing sections creates no plaintext file at all; clicking "Sync now" makes the file appear only while the mocked sync runs and disappear immediately after, confirmed via the log showing zero real adapter calls. All test keychain entries and the test data directory were deleted afterward.

5b. ✅ Bug fix: "Refresh" in Garmin/Divelogs Dives showed nothing, ever, with no error.
   - **Root cause**: `dive_cache.list_garmin_dives()`/`list_divelogs_dives()` (what Refresh calls) only read per-dive JSON cache files. Nothing populates those files except `SyncEngine.download_and_save_raw_data()` — a distinct method the old web UI exposed as a separate "Download Raw Data" button, but which milestone 1's trim removed and no later milestone rebuilt for desktop. "Sync now" fetches dives into memory for matching/pushing only; it never writes that cache. So Refresh was working correctly — there was just never anything for it to find, and no feedback said so either way.
   - **Fix**: `src/core/scheduler.py` gained `run_download_thread()`/`is_download_running`/`last_download_results`, mirroring `run_sync_thread`. `desktop/sections/sync.py` gained a "Download dives" button (+ an "Overwrite existing cache" switch, default off to avoid clobbering local edits that failed to push) next to "Sync now", sharing the same log panel/progress bar; the two buttons disable each other while either is running (extracted the shared thread-start+poll-log-drain logic into `_run_background_job()`). `DiveEditorSection.on_save`/`on_delete` also now check `scheduler.is_download_running` (in addition to `is_sync_running`) before proceeding, since a download rewrites the same cache files being edited.
   - Verified live: mocked `download_and_save_raw_data` to write one fake dive file without any real network call — clicked "Download dives", watched both buttons disable, log stream, "Download complete." status, then navigated to Garmin Dives, clicked Refresh, and confirmed the fake dive appeared. Real keychain confirmed untouched afterward.
